# 成功条件と失敗例

これらは比較実験で目指す条件です。実機で確認した結果と、予定した検査に到達しなかったケースは[実行結果](results.md)に記録しています。
入力とケース一覧は[共通fixture](../fixtures/training-completion.json)と[cases.json](../fixtures/cases.json)に記載しています。

## 通常ケースの成功条件

1. 発行者が共通データから署名付き証明を発行し、保有者のソフトウェアが受領して保存できる。
2. 検証者が提示要求を送り、保有者がname、courseId、completedOnを開示して応答できる。
3. 検証者が発行者の署名、保有者の鍵、期限、nonceとaudienceを確認できる。
4. 設定済みの信頼する発行者とSEC-101であることを確認し、必要属性と申込情報の照合を経てACCEPTを記録できる。
5. 検証者に届く証明と開示情報にemailの値を含めないことを確認できる。

申込情報の本人確認は前提条件です。氏名の一致だけで実在の人の同一性を保証しません。
最終結果は「APIから200が返った」だけで判断せず、各確認の成否と業務側の判定を記録します。

## 失敗ケース

| ID | 期待する結果 | 原因を判定する段階 |
|---|---|---|
| tampered-claim | 拒否 | 発行後に変更した開示値のダイジェスト不一致 |
| expired | 拒否 | 正しく署名された証明の期限切れ |
| wrong-holder-key | 拒否 | 発行時の保有者公開鍵と提示の署名が合わない |
| untrusted-issuer | 拒否 | 暗号検証は成功しても、発行者が信頼対象外 |
| missing-required-claim | 拒否 | 必須のnameが提示されない |
| wrong-course | 拒否 | 暗号検証は成功しても、研修がSEC-101ではない |
| wrong-nonce | 拒否 | 提示要求とnonceが合わない |
| wrong-audience | 拒否 | 提示先が現在の検証者ではない |
| missing-key-binding | 拒否 | 教材で要求する保有者の鍵の確認ができない |

一度に変える条件は一つにし、狙った確認段階まで到達した証拠を残します。
たとえば設定不備で発行に失敗した結果を、期限切れを拒否できた結果として数えません。
構文エラーで止まった場合も、想定した暗号検証や業務判断を確認したことにはしません。

同じ証明の別属性を隠すケースも作れるように、実装時は必要属性を選択的開示の対象にします。
OSSで必要な操作ができない場合はUNSUPPORTED、まだ試していない場合はNOT_RUNと記録します。
外付けの検証処理や業務判定を追加した場合は、OSS本体の機能と区別します。

## 後続回で追加するケース

失効、状態情報の取得失敗、更新、再発行、鍵の復旧、別OSSとの接続は後続回で扱います。
準備版の成功条件には含めず、未検証として残します。
